🏗️ 這個 App 怎麼運作

三個模組

  • 耳朵（ASR） — 瀏覽器原生 Web Speech API，連續辨識、即時回傳中間結果。Chrome 會把音訊送到 Google 伺服器做辨識。
  • 大腦（LLM） — Gemini streamGenerateContent，SSE 逐字回傳。已關閉 thinking，換取最短首字延遲。
  • 嘴巴（TTS） — 瀏覽器原生 speechSynthesis，音色由作業系統提供。

難的不是三個模組，是讓對話絲滑

  • 流式響應 — 不等 LLM 講完整段。邊收字邊切句，湊滿一個完整句子就立刻丟給 TTS 排隊唸。首次出聲從「等三秒」變成「等半秒」。
  • 延遲判停（endpointing） — 人講話會停頓，不能一停就當講完。這裡用靜音計時器：最後一次辨識到聲音後，靜音超過設定的毫秒數才算一輪結束。太短會插你的話，太長顯得遲鈍。
  • 插話打斷（barge-in） — 外教朗讀時麥克風不關，一偵測到你開口就同時做三件事：speechSynthesis.cancel() 停嘴、AbortController.abort() 中斷還在生成的 LLM 串流、把已講出口的半句寫回對話歷史（讓 AI 知道自己被打斷在哪）。
  • 回音問題 — 外放時麥克風會收到 TTS 自己的聲音，被誤判成插話。這裡用文字比對過濾：辨識結果如果和正在朗讀的內容高度重疊就丟掉。戴耳機可以關掉這層防護，打斷會更靈敏。

為什麼不直接用端到端語音模型

端到端模型（GPT 語音、豆包、千問）延遲短、體驗好，但難以客製。要套進具體的教學或商業場景，人設、課程、糾錯邏輯、記憶都得能改。拆成模組雖然要自己處理絲滑度，但每一層都能換、能調。技術終局大概是「端到端模型 + skill + tool」— 用外接技能和工具補上客製化與記憶。

成本

ASR 和 TTS 都是瀏覽器原生功能，不用錢。只有 LLM 走 Gemini API 計費，一般對話練習用 flash 模型單次成本極低。
